# Changes — 06-04-26 (Session 9)

## Improved Transparency Fallback for Windows/NVIDIA Compatibility

### 90. Robust transparency compositing fallback

**Modified:** `src/SvalboardLayerViz.App/Views/MainWindow.axaml`, `src/SvalboardLayerViz.App/Views/MainWindow.axaml.cs`

- On some Windows systems (especially with NVIDIA GPUs), Avalonia reports transparency as available (`ActualTransparencyLevel == Transparent`) but the compositor doesn't actually render the surface — resulting in a fully invisible window
- Added a multi-level `TransparencyLevelHint` fallback chain: `Transparent,AcrylicBlur,None`
- Replaced the simple `None`-only check with `ApplyTransparencyFallback()`:
  - **None**: Falls back to solid `#1E1E2E` background (matching the status bar) with system decorations
  - **Transparent on Windows**: Applies a near-transparent safety background (alpha=1/255) — invisible to humans but prevents NVIDIA compositors from discarding the surface
  - **Other cases** (AcrylicBlur, macOS, etc.): No change needed
- Addresses user report: app starts but only shows a tray icon and task manager process, no visible window (Windows, NVIDIA 4070 Super, 1080p)

### 91. Software rendering escape hatch

**Modified:** `src/SvalboardLayerViz.App/Program.cs`

- Added `SVALBOARD_RENDER_MODE` environment variable: set to `software` to force software rendering as a workaround for GPU driver issues
- When unset, Avalonia uses its default rendering pipeline (AngleEgl with Software fallback)

### 92. Startup diagnostic logging

**New file:** `src/SvalboardLayerViz.Core/Diagnostics/StartupLogger.cs`

- Lightweight file logger for diagnosing rendering issues — no external dependencies
- Logs OS, architecture, .NET runtime, rendering mode, transparency level, and fallback decisions
- Auto-truncates at ~100 KB to prevent unbounded growth
- All writes are try/catch wrapped so logging never crashes the app

**Log file location:**

| OS | Path |
|---|---|
| **Windows** | `%AppData%\SvalboardLayerViz\startup.log` — Open File Explorer, paste `%AppData%\SvalboardLayerViz` into the address bar |
| **macOS** | `~/Library/Application Support/SvalboardLayerViz/startup.log` — In Finder: Go menu → Go to Folder (Shift+Cmd+G), paste `~/Library/Application Support/SvalboardLayerViz` |
| **Linux** | `~/.config/SvalboardLayerViz/startup.log` — Open a terminal and run `cat ~/.config/SvalboardLayerViz/startup.log` |

### 93. `RenderingMode` setting in settings.json

**Modified:** `src/SvalboardLayerViz.Core/Settings/UserSettings.cs`, `src/SvalboardLayerViz.App/Program.cs`

- Added `RenderingMode` property to `UserSettings` (default: `"auto"`)
- Users can set `"software"` in `settings.json` to force software rendering persistently, instead of needing to set the environment variable before every launch
- Environment variable `SVALBOARD_RENDER_MODE` still takes precedence over the settings file
- The startup log shows which source the rendering mode came from (env var vs settings.json)

### 94. Startup flow tracing

**Modified:** `src/SvalboardLayerViz.App/App.axaml.cs`, `src/SvalboardLayerViz.App/Views/MainWindow.axaml.cs`

- User's startup log revealed the `Opened` event never fires — the window isn't reaching the visible state at all, ruling out transparency as the root cause

## Deferred Device Connection & Async HID Enumeration

### 95. Deferred device connection to unblock window creation

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`, `src/SvalboardLayerViz.App/App.axaml.cs`

- **Root cause found**: User's startup log stopped at `"Creating MainWindowViewModel..."` — the constructor called `TryConnect()` synchronously, which calls HidSharp's `DeviceList.Local.GetHidDevices()`. On the affected Windows 11 system, HID enumeration hangs indefinitely, blocking the constructor and preventing the window from ever being created
- Removed `TryConnect()` and `OnDeviceListChanged()` from the `MainWindowViewModel` constructor
- Added `InitializeDeviceConnection()` public method containing both calls
- `App.axaml.cs` calls it via `Dispatcher.UIThread.Post(..., DispatcherPriority.Background)` after all window setup is complete — window appears immediately, device connects shortly after

### 96. Async device enumeration with 10-second timeout

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Replaced synchronous `TryConnect()` with `TryConnectAsync()`
- HID enumeration runs on a background thread via `Task.Run()` with a 10-second `CancellationTokenSource` timeout
- If enumeration hangs (as on the affected Windows system), the app shows "Device search timed out — click Refresh to retry" instead of freezing forever
- `RefreshCommand` and `OnDeviceListChanged` callback both use the async version

### 97. Concurrency guard for device connection

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- HidSharp fires a burst of 13-17 `DeviceListChanged` events at startup, each spawning a `TryConnectAsync()` call
- Multiple concurrent HID reads corrupt each other, causing "Invalid XZ Stream" and "Data Error" exceptions
- Added `_isConnecting` boolean guard — only one `TryConnectAsync()` runs at a time, subsequent calls are silently skipped
- Added `_connectCts` to cancel any in-flight enumeration when a new attempt starts

### 98. Layer 0 auto-selection fix after async refactor

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- After the async refactor, `SelectedLayerIndex = 0` no longer triggered a property change notification because the default value is already 0 — CommunityToolkit.Mvvm skips notifications when the value is unchanged
- Fixed by setting `SelectedLayerIndex = -1` then `SelectedLayerIndex = 0` to force the notification (same pattern already used in `ApplySettings()`)

### 99. Granular per-device HID logging

**Modified:** `src/SvalboardLayerViz.Core/Device/DeviceConnectionService.cs`

- Added per-device logging during HID enumeration to diagnose which specific USB device causes hangs
- VID/PID is logged **before** any USB I/O calls (`GetFriendlyName()`, `GetReportDescriptor()`) — if a subsequent call hangs, the last log line identifies the culprit device
- Each device produces 2 log lines: VID/PID identification, then result (Vial match, skip, or error)
- Stays well within the 100 KB log file limit even with many USB devices

### 100. Localization: device search timeout message

**Modified:** `src/SvalboardLayerViz.App/Resources/Strings.resx`, `Strings.nl.resx`

- Added `Status_DeviceSearchTimedOut` key: "Device search timed out — click Refresh to retry" (EN) / "Apparaat zoeken verlopen — klik Vernieuwen om opnieuw te proberen" (NL)

### 101. Full protocol I/O moved to background thread

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Previous fix (#96) only ran HID enumeration on a background thread — the Vial protocol exchange (`loader.Load()`: connect, read keymap, XZ decompression) still ran on the UI thread and blocked it
- Windows user confirmed: window appears but immediately hangs after the help screen (enumeration completes fine, hang is in the protocol exchange)
- Expanded `Task.Run` to cover all HID I/O: enumeration, protocol connect, keymap loading, decompression, and QMK settings read
- Returns a result object from the background thread; only observable property updates run on the UI thread after awaiting
- Increased timeout from 10s to 30s to cover the full protocol exchange

### 102. Prefer Svalboard when multiple Vial devices are connected

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- With multiple Vial devices connected (e.g. Moonlander + Svalboard), the app previously picked `devices[0]` which happened to be the Moonlander — its protocol exchange caused the hang
- Added `PickPreferredDevice()`: prefers any device whose `ProductName` starts with "lightly" (case-insensitive), falls back to the first device
- Handles future name changes ("Lightly New", "lightly v2", etc.) via prefix matching
- Disconnecting the Moonlander confirmed as the user's workaround; this fix makes it automatic

### 103. Live keys status message duplication fix

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- `StartMatrixPolling()` appended `" | Live keys ON"` to `StatusMessage` each time it was called
- Toggling live highlighting off/on kept stacking the suffix (e.g. "Connected | Live keys ON | Live keys ON")
- Replaced the append with `RefreshStatusMessage()` which builds the status string from scratch
- Added `RefreshStatusMessage()` call in `ToggleLiveHighlighting()` to update status in both directions
