### 179. ApplySaveResult(SaveSuccess) — rebuild edit session on reloaded baseline

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- The Session 11 success branch nulled `_editSession` while leaving `IsEditMode = true`, breaking the invariant that `_editSession` is non-null whenever edit mode is on. `OnKeyClicked` early-returns on `_editSession is null`, so every post-save click was silently dropped — the app appeared frozen until restart

### 180. ReloadKeymapFromDeviceAsync — in-place VM tree update

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`, `src/SvalboardLayerViz.App/ViewModels/LayerViewModel.cs`, `src/SvalboardLayerViz.App/ViewModels/KeyViewModel.cs`, `src/SvalboardLayerViz.App/ViewModels/KeyClusterViewModel.cs`, `src/SvalboardLayerViz.App/Views/ThumbClusterView.axaml`

- Second post-save bug surfaced after fix 179: after a save, the displayed label on the edited key refused to update on a *second* edit until app restart. Root cause was that `ReloadKeymapFromDeviceAsync` called `BuildLayerViewModels` which replaced the entire VM tree; the creative thumb-cluster layout binds borders via hardcoded DataContext paths (`{Binding Keys[2]}` etc.) and those paths silently kept pointing at the previous, detached VM instances
- `MainWindowViewModel.ReloadKeymapFromDeviceAsync`: when `Layers.Count > 0` update existing layer VMs in place via the new `LayerViewModel.UpdateBaselineFromLayer(newLayer)` helper instead of rebuilding; only fall back to `BuildLayerViewModels` on first-load
- `LayerViewModel.UpdateBaselineFromLayer`: matches each existing `KeyViewModel` to the fresh `Layer.Keys` entry by `(Row, Col)` and delegates to the new `KeyViewModel.UpdateBaseline(newKey)` helper
- `KeyViewModel.Key` is now `private set`; `UpdateBaseline(Key newKey)` swaps the backing `Key` and fires a broadcast `OnPropertyChanged(string.Empty)` so every derived binding (labels, tooltip, hex, background) re-evaluates without replacing the instance
- `KeyClusterViewModel` exposes named `Thumb0`–`Thumb5` accessors wrapping `Keys[0..5]` so the creative thumb layout can bind by name; indexer bindings were the fragile path that broke after the VM swap, named properties re-resolve reliably with Avalonia's compiled bindings
- `ThumbClusterView.axaml`: all 12 creative-layout borders (left + right hand × 6 thumb keys) switched from `{Binding Keys[N]}` to `{Binding ThumbN}`

### 184. PreSaveSafetyCheck — drop NoLayerEscape, add auto-mouse heuristic

**Modified:** `src/SvalboardLayerViz.Core/Keymap/PreSaveSafetyCheck.cs`, `src/SvalboardLayerViz.Tests/Keymap/PreSaveSafetyCheckTests.cs`

- Removed the `SafetyWarningKind.NoLayerEscape` enum value and all detection code (including the `hasLayerSwitch` tracking in the main loop). The warning was too noisy in practice — a non-base layer with a transparent cell over a base-layer MO still has a valid escape, and the static scan couldn't see that. Five corresponding tests removed from `PreSaveSafetyCheckTests`
- Added `LooksLikeMouseLayer(keymap, layer, rows, cols)` helper and wired it into the unreachable-layer scan. QMK's auto-mouse feature activates a dedicated layer on trackball movement *without* any layer-switch keycode referencing it, so such layers look unreachable by static analysis but are fine in practice. Heuristic: layer is treated as auto-mouse target if it contains at least `MouseKeyThreshold = 2` mouse basic keycodes in the `0x00CD..0x00DC` range
- Two new tests: `Check_UnreachableMouseLayer_NoWarning` (three mouse keys on otherwise-unreachable layer → no warning) and `Check_UnreachableLayerWithOneMouseKey_StillWarns` (single mouse key on a letters layer → still warns)

## Picker — Empty, Transparent, and named QMK specials in Basic catalog

### 187. SpecialKeycode descriptor + KeycodeCatalog.NamedSpecialKeycodes

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeycodeDescriptor.cs`, `src/SvalboardLayerViz.Core/Keymap/KeycodeCatalog.cs`, `src/SvalboardLayerViz.Core/Keymap/KeycodeDecoder.cs`, `src/SvalboardLayerViz.Core/Keymap/KeycodeEncoder.cs`, `src/SvalboardLayerViz.Core/Keymap/KeycodeService.cs`

- New `public record SpecialKeycode(ushort Code)` for named QMK keycodes that don't fit any structured range — currently `QK_REPEAT_KEY` (`0x7C79`) and `QK_LAYER_LOCK` (`0x7C7B`). Extensible by adding entries to `NamedSpecialKeycodes`
- `KeycodeCatalog.NamedSpecialKeycodes` dict (`ushort → label`) — the resolver path for `SpecialKeycode.Code → label`, excludes 0x0000/0x0001 which have their own dedicated descriptors
- `KeycodeCatalog.SpecialKeys` catalog list — `Empty` (0x0000), `▽` (0x0001), `Repeat` (0x7C79), `LyrLk` (0x7C7B) — used by the picker to render these four keys in the Basic grid without inventing a new category. Intentionally NOT merged into `AllGroups` so the per-basic-code `BasicKeycodes` lookup dict stays free of full 16-bit codes
- `KeycodeDecoder.Decode`: new check runs right after the 0x0000/0x0001 special-cases and before the `<= 0x00FF` basic range, so Repeat/LayerLock emit `SpecialKeycode` instead of falling into `CustomKeycodeDescriptor` (they're outside the 0x7E00+ QK_KB range but wanted to be sure)
- `KeycodeEncoder.Encode`: new switch arm `SpecialKeycode s => s.Code`
- `KeycodeService.Resolve`: new switch arm emits `KeycodeInfo` with label from `NamedSpecialKeycodes.GetValueOrDefault(s.Code, $"0x{s.Code:X4}")`
