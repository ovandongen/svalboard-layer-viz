# Changes — 12-04-26-g (Phase 4b Session 5 — QMK Settings Protocol Fix + Investigation)

## QMK Settings: query parsing fix, catalog-derived widths, diagnostic logging

Thorough investigation with real device revealed root cause of QMK settings mismatches: query response was parsed at 4-byte stride (QSID + width) but firmware actually sends 2-byte entries (QSID only, no width). This caused skipped QSIDs, wrong widths, and garbage values for u8 settings. Also added env-var-controlled debug logging and verified all values against firmware raw bytes.

### 246. Query response: 2-byte stride, not 4-byte

**Modified:** `src/SvalboardLayerViz.Core/Protocol/VialProtocolService.cs`
**Modified:** `src/SvalboardLayerViz.Core/Protocol/IVialProtocolService.cs`

- `GetQmkSettingsList()` return type changed from `IReadOnlyList<(ushort Id, byte Width)>` to `IReadOnlyList<ushort>` — firmware query response contains ONLY u16 QSIDs at 2-byte stride, terminated by 0xFFFF fill bytes
- Was parsing at 4-byte stride assuming `(QSID u16, width u16)` pairs — this skipped every other QSID and treated the next QSID's bytes as width
- Confirmed by reading vial-qmk `qmk_settings.c` source: `qmk_settings_query()` writes only QSIDs
- Result: 26 QSIDs now discovered (was 13), all settings visible

### 247. Width derived from catalog, not firmware

**New method:** `src/SvalboardLayerViz.Core/QmkSettings/QmkSettingsCatalog.cs` — `GetWidth(ushort id)`

- Since firmware query doesn't include width, it must come from the catalog
- Scalar settings: UInt8/Boolean → 1 byte, UInt16 → 2 bytes
- Bitfield QSIDs: width of parent field based on max bit index (< 8 → 1 byte, >= 8 → 2 bytes)
- Unknown IDs default to 2 (u16)
- Updated `KeymapLoader.cs` and `MainWindowViewModel.cs` (post-save re-read) to use `QmkSettingsCatalog.GetWidth(id)`

## Device verification: our values vs Keybard vs firmware raw bytes

Connected to real Svalboard ("lightly"), captured raw protocol data at debug level. All 26 firmware QSIDs queried, 24 returned values, 2 unsupported (TapCodeDelay 0x0012, FlowTapTerm 0x001B — firmware advertises but returns all-zero).

| Setting | Keybard | Our App | Firmware Raw | Verdict |
|---|---|---|---|---|
| Permissive Hold | ON | OFF | 0x00 | **Keybard bug** |
| Retro Tapping | ON | OFF | 0x00 | **Keybard bug** |
| Ignore Mod Tap | shows | missing | no QSID 0x08 | Expected (old protocol) |
| Tapping Force Hold | shows | missing | no QSID 0x08 | Expected (old protocol) |
| Tap Code Delay | 0 | missing | all-zero (unsupported) | Correct to skip |
| Hold On Other Key Press | OFF | OFF | 0x00 | Match |
| Quick Tap Term | missing | 200ms | 0xC8 = 200 | Correct (new QSID) |
| Chordal Hold | missing | OFF | 0x00 | Correct (new QSID) |

**Conclusion:** Our values are correct. Keybard uses old QSID 0x08 (packed tapping_v2 bitfield) which may have stale bits; firmware doesn't even report 0x08 in its query response. The remaining presence/absence differences are expected — keybard doesn't know about newer QSIDs (0x17, 0x19, 0x1A), and we correctly don't show the legacy 0x08 bitfield names.
