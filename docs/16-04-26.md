## Code-review round — data-drives-UI, robustness, perf, tests

A thorough review (plan: `starry-popping-biscuit`) flagged findings across three buckets — (1) data-drives-UI violations where the VM layer was patching Core-owned data at render time, (2) correctness gaps (unbounded matrix reads, race conditions, codec failures crashing dialogs, missing validations), (3) perf hot loops doing O(n²) lookups. Entries 313–329 land every fix from that plan plus the companion test expansion (299 → 1156 tests, +~150 new assertions). Nothing in the plan got deferred.

### 313. Thumb key labels not refreshing after save/Refresh — extract `ThumbKeyView` UserControl

**Added:** `src/SvalboardLayerViz.App/Views/ThumbKeyView.axaml`, `src/SvalboardLayerViz.App/Views/ThumbKeyView.axaml.cs`
**Modified:** `src/SvalboardLayerViz.App/Views/ThumbClusterView.axaml`

- Symptom: after editing a thumb key and saving — or pressing Refresh — the new label did not appear on the creative-layout thumb button. Only a full app restart showed it. Finger keys did not have this problem.
- Root cause: the creative thumb layouts rendered each key via an inline `<ContentPresenter ContentTemplate="{StaticResource ThumbKeyContent}" Content="{Binding}" />` sitting inside a reused `<Border>`. When the `KeyViewModel` swapped (either via `UpdateBaselineFromLayer` broadcasting `PropertyChanged(string.Empty)`, or via `BuildLayerViewModels` wholesale replacing the parent `KeyClusterViewModel`), the `ContentPresenter`'s label `TextBlock`s didn't re-resolve their bindings cleanly. Finger keys use `<views:KeyView />` via `ItemsControl`, whose items are regenerated on source change and whose own compiled bindings refresh correctly — hence the asymmetry.
- Fix: mirror the finger pattern by introducing a real `ThumbKeyView` UserControl (`x:DataType="vm:KeyViewModel"`) containing the same ToolTip, ContextMenu, and three label `TextBlock`s with drop-shadow effects. In `ThumbClusterView.axaml`, replace all 12 `<ContentPresenter … />` children (6 in `LeftCreativeLayout` + 6 in `RightCreativeLayout`) with `<views:ThumbKeyView />`, and drop the now-unused `UserControl.Resources` + `ThumbKeyContent` `DataTemplate`. DataContext still flows through each `Border` (`DataContext="{Binding ThumbN}"`); the UserControl's own compiled bindings re-resolve cleanly on VM swap.
- `Tapped="OnThumbKeyTapped"` hoisted from the old template's inner `Grid` onto each of the 12 `Border`s so click-to-edit keeps working (`OnThumbKeyTapped` reads `(sender as Control)?.DataContext as KeyViewModel`, which resolves the same way from either host).
- All `Border.Clip` `PathGeometry` cutouts (Thumb2 trapezoid with C:4 bite + C:5 hole, Thumb3/Thumb1/Thumb0 narrowing edges) preserved verbatim. No behavioural change to the layout; only the rendering-host mechanism changes.

### 314. `KeyViewModel._style` recomputed on `UpdateBaseline`

**Modified:** `src/SvalboardLayerViz.App/ViewModels/KeyViewModel.cs`

- Companion fix surfaced while diagnosing 313. `_style` (the `KeyStyleResolver.Resolve` result driving `BackgroundColor`, `BorderColor`, `TextColor`, `KeyOpacity`) was `readonly` and computed once in the constructor. After `UpdateBaseline(newKey)` the `Key` got replaced and a broadcast `PropertyChanged(string.Empty)` fired, but `_style` kept the *old* key's category tints. Labels looked right (they read `Key.*` directly), but colours lied whenever the new keycode changed category: plain → layer-switch (should tint toward target-layer colour), plain → transparent (should dim), layer-switch → plain (should drop the target tint), and so on.
- Fix:
  - Drop `readonly` on `_style`.
  - Cache what `KeyStyleResolver.Resolve` needs per key: `_ownLayerColors` (layer index doesn't change, so this is a true one-shot), plus references to `_palette` / `_totalLayers` / `_userLayerColors` / `_deviceLayerColors` so target-layer colours can be re-resolved when a keycode switches to a layer-switch pointing elsewhere.
  - Extract `ResolveTargetLayerColors(Key)` — same palette-first, device-HSV+user-override fallback logic as the constructor used inline. Called from both ctor and `UpdateBaseline`.
  - `UpdateBaseline` now: `Key = newKey; _style = KeyStyleResolver.Resolve(newKey, Layer.Index, _ownLayerColors, ResolveTargetLayerColors(newKey)); OnPropertyChanged(string.Empty);`.
- Net cost per edit-save: one `KeyStyleResolver.Resolve` call (cheap — pure branching on `Key` flags, no HSL→RGB) + one palette lookup when the new key is a layer-switch. Zero extra work for non-swapped keys since `UpdateBaseline` is called per reloaded `Key` anyway.

### 316. `MacroEditorViewModel` — kill dead unsubscribe + the mirror/resync pattern

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MacroEditorViewModel.cs`

- Was: `SelectedSlot.Actions.CollectionChanged -= null!; SelectedSlot.Actions.Clear(); foreach (var vm in SelectedActions) SelectedSlot.Actions.Add(vm.Action);`. The `-= null!` was a no-op (nothing was ever subscribed in this class), the comment was a lie, and the full Clear/refill gave you two sources of truth — the VM's `SelectedActions` mirror and the underlying `SelectedSlot.Actions` — which had to be hand-synced on every edit.

### 317. Combo + tap-dance editor row-VMs survive corrupt device data

**Modified:** `src/SvalboardLayerViz.App/ViewModels/ComboEditorViewModel.cs`, `src/SvalboardLayerViz.App/ViewModels/TapDanceEditorViewModel.cs`

- `ComboCodec.Decode(bytes)` and `TapDanceCodec.Decode(bytes)` run inside each row-VM ctor. Before: a single malformed entry from firmware threw out of the constructor and took the whole dialog down before it opened — worst possible time to fail.
- Wrapped both decodes in try/catch; on failure log `DiagnosticLog.Warn("Combo"/"TapDance", $"Slot {index} decode failed ({ex.Message}); showing empty.")` and fall back to `Combo.Empty` / `TapDance.Empty`. Other slots still load.
- Also: `TapDanceRowViewModel` had raw `_suppressTermCallback = true; TappingTerm = …; _suppressTermCallback = false;` in two places (ctor seed + `ClearSlot`). ### 318. `MainWindowViewModel` — matrix bounds-check + LED-poll/save race

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- `OnMatrixStateChanged` does four nested reads of `state[row, col]` plus one of `_previousMatrixState[row, col]`. None were bounds-checked. If the device reconnected with a differently-sized matrix (firmware swap, different board plugged in), an `IndexOutOfRangeException` would propagate out of a background-thread callback and crash the process. Added `state.GetLength(0)` / `GetLength(1)` caps at the top of the handler, a dimension-match guard before touching `_previousMatrixState`, and per-loop `continue` guards for every cached-key iterator (toggle cache, momentary cache, render loop).
- `OnLedColorChanged` now short-circuits on `IsSaving`, both on entry and inside the `Dispatcher.UIThread.Post` continuation. During a save, the save flow itself reloads the keymap and flips `SelectedLayerIndex`; an LED-poll fired in the same window was racing it and leaving the UI on the wrong layer.

### 321. `LayerColorPalette` — precompute layer colors once, look up O(1) per key

**Added:** `src/SvalboardLayerViz.App/ViewModels/LayerColorPalette.cs`
**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`, `LayerViewModel.cs`, `HandViewModel.cs`, `KeyClusterViewModel.cs`, `KeyViewModel.cs`

- `LayerColorService.GetLayerColors` (HSL → RGB) was being invoked from `KeyViewModel`'s ctor for the key's own layer and again for the target layer on any layer-switch keycode. 60 keys × N layers × ~2 calls per load — about a thousand HSL→RGB conversions per keymap reload, all producing the same N `LayerColors` values.
- New `LayerColorPalette(layers, userLayerColors)` builds a `Dictionary<int, LayerColors>` once — N HSL→RGB calls total. Threaded through the VM constructor chain (`MainWindowViewModel.BuildLayerViewModels` → `LayerViewModel` → `HandViewModel` → `KeyClusterViewModel` → `KeyViewModel`) as an optional `palette` parameter; existing callsites pass null and keep the legacy path for compatibility.
- `KeyViewModel.Get(layer.Index)` for own layer + `palette.Get(targetLayer)` for layer-switch keys — both O(1). UX identical (layer-switch keys still tint toward the target layer's colour, which is a valuable learning cue), cost is now N HSL→RGB per load instead of ~1000.
- `LayerColorPalette.Get(index)` also handles out-of-range target layers (a layer-switch pointing beyond the configured range) via the algorithmic default fallback.

### 322. `TransparentKeyResolver` — O(keys²) → O(keys · layers)

**Modified:** `src/SvalboardLayerViz.Core/Keymap/TransparentKeyResolver.cs`

- Worst case was `layers × keys × layers × FirstOrDefault(O(keys))` — quadratic in keys per layer. Replaced with a `Dictionary<(int Row, int Col), Key>[]` built once per resolve call: one dict per layer, populated upfront. The inner lookup becomes `indexByLayer[below].TryGetValue((row, col), out var lowerKey)`.
- Also simplified control flow — early `continue` on transparent lower-layer match, and on dict miss, replacing the nested-if ladder.
- New `TransparentKeyResolverDeepTests` file added (179 LOC) covering 8+-deep TRNS stacks, TRNS with no underlying match at all (behaviour: leave the key alone), and default-layer ≠ 0 resolution order.

### 323. `KeymapLoader` — physical-position lookup out of the hot loop

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeymapLoader.cs`

- `SvalboardLayout.GetKeyPositions().FirstOrDefault(p => p.Row == row && p.Col == col)` was inside the (layers × rows × cols) decode loop — so for an 8-layer load with 10×6 matrix that's 480 linear scans of the 60-entry position list. Pulled into a single `ToDictionary(p => (p.Row, p.Col))` before the loop; inner lookup becomes `physicalLayout.TryGetValue((row, col), out var position)`.

### 327. `MacroCodec` — delay parser refuses to guess on corrupt firmware output

**Modified:** `src/SvalboardLayerViz.Core/Macros/MacroCodec.cs`, `src/SvalboardLayerViz.Tests/Macros/MacroCodecTests.cs`

- Delay decode (SS_DELAY_CODE → collect ASCII digits → expect `|` terminator) had two silent failure modes: (a) a non-digit byte in the digit stream was coerced via `(char)buffer[pos++]` and then `int.Parse`'d on the accumulated string, which would throw `FormatException` deep in the caller rather than at the parser boundary; (b) hitting the buffer end or a macro terminator before the `|` silently treated the truncated value as complete.
- Both paths now throw `InvalidDataException` with message including the macro index and the offending byte: `"Macro {macroIdx}: non-digit 0x{X2} in delay value."` and `"Macro {macroIdx}: delay value missing '|' terminator."`. Structured diagnostics, caller can catch and recover without parsing.
- Test `Decode_DelayTerminatedByEndOfMacro` (which asserted the old silent-recovery behaviour) flipped to `Decode_DelayMissingPipeThrows`. Still one test, still the same fixture bytes — the contract just inverted.

### 328. `VialProtocolService` — testability hook + empty-result guard
