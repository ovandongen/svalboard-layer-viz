### 345. `SendCommand` short-read bounds — `ExtractResponse` static helper

**Modified:** `src/SvalboardLayerViz.Core/Protocol/VialProtocolService.cs`, `src/SvalboardLayerViz.Tests/Protocol/VialProtocolServiceParserTests.cs`

- `SendCommand`'s read path computed `dataOffset = bytesRead > ReportSize ? 1 : 0` then `Array.Copy(readBuffer, dataOffset, response, 0, ReportSize)` with no check that `bytesRead >= dataOffset + ReportSize`. On a short firmware read (e.g. cable glitch returns 16 bytes), the copy padded the response with the uninitialised tail of `readBuffer`. Downstream parsers — `GetLayerCount` (reads `response[1]`), `GetKeyboardId` (`BitConverter.ToUInt64(response, 0)`), the keymap chunk loop — saw plausible-looking zeros and produced silent garbage.
- Of the five `Array.Copy` sites in this file, only `SendCommand`'s is at risk; the four chunk-readers (`GetDefinition`, `GetKeymapBuffer`, `GetMacroBuffer`, `ReadDynamicEntry`) all source from `SendCommand`'s already-32-byte response with hardcoded offsets bounded by `ReportSize - dataOffset`. So the fix lives at the gateway.
- Extracted the report-ID-detection + copy into `internal static byte[] ExtractResponse(byte[] readBuffer, int bytesRead)`. New floor check: `if (bytesRead < dataOffset + ReportSize) throw new IOException($"Short HID read: expected {required}, got {bytesRead}")`. `IOException` because that's the BCL idiom for "stream returned less than expected"; downstream caller can either fail-loud or wrap in retry logic — neither was possible with the silent-pad behaviour.
- `internal` (not `private`) so tests reach it via `InternalsVisibleTo SvalboardLayerViz.Tests` (already wired in `Core.csproj`). Direct unit test on `SendCommand` would have required mocking `HidStream`, which HidSharp doesn't make easy. Three new tests in `VialProtocolServiceParserTests`: full read with no report-ID byte, full read with report-ID byte (asserts the leading 0xAA is stripped), short read of 16 bytes (asserts `IOException` with "Short HID read" + "16" in message).
- Also added a docstring to `ExtractResponse` documenting *why* the report-ID detection works by length comparison (Windows prepends, macOS/Linux don't) — the original ternary was correct but the reasoning was implicit.

### 346. `_connectCts` per-attempt dispose-and-replace

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- `TryConnectAsync` opened with `_connectCts?.Cancel(); _connectCts = new CancellationTokenSource(...)` — cancelled the prior attempt's CTS but never disposed it, leaking one `CancellationTokenSource` per device-list event. Entry 341's `Shutdown()` does dispose the field, so the leak was bounded by reconnect-cycles-between-shutdowns, but every USB hot-plug between launch and quit accumulated one orphan CTS.
- The `finally` block at the bottom only reset `_isConnecting = false`; it didn't dispose the in-flight CTS either. Normal completion paths (success, no-device-found, OperationCanceledException, generic-exception) all left a live CTS hanging until the next attempt or shutdown.
- New entry pattern: capture `_connectCts` into `oldCts` local, allocate `attemptCts` and assign it to `_connectCts` *first*, *then* `oldCts?.Cancel()` + `oldCts?.Dispose()`. Order matters — the assign-before-dispose window means a concurrent observer (currently impossible because of `_isConnecting` early-exit, but cheap defence-in-depth) never sees `_connectCts` as `null` mid-swap.
- New finally pattern: dispose `attemptCts` only if `ReferenceEquals(_connectCts, attemptCts)`. If a newer attempt has supplanted us, the newer attempt already disposed our CTS as its `oldCts` — double-dispose would throw. Captured-local pattern is the standard .NET idiom for "dispose the thing this scope owns, not whatever the field happens to point at now".
- Verified the Shutdown interleave: Shutdown sets `_connectCts = null` after disposing; the finally's `ReferenceEquals` check evaluates false (field is null, local is the now-disposed CTS), so we skip the redundant dispose. Safe both ways.
- No new test. The fix is local, the dispose-and-replace pattern is well-known, and a meaningful unit test would require either constructing the full `MainWindowViewModel` (heavy: ~10 service dependencies) or extracting the swap into its own helper (over-engineering for three lines). Added an XML `<remarks>` block on `TryConnectAsync` describing the lifecycle so the next reader doesn't have to reconstruct the reasoning.

### 347. `HidStream.Close()` before `Dispose()` + `_disposed` guard

**Modified:** `src/SvalboardLayerViz.Core/Protocol/VialProtocolService.cs`

- `Dispose()` called only `_stream?.Dispose()`, never `_stream?.Close()`. `HidStream` (HidSharp 2.6.4) inherits from `System.IO.Stream`; the BCL contract guarantees `Stream.Close()` is idempotent and `Close()` calls `Dispose(true)` so `Close` then `Dispose` collapses to two `Dispose(true)` invocations of which the second is a no-op. Skipping `Close` is technically allowed but on cable yank the OS handle sometimes lingers until GC finalisation, blocking the next `device.Open()` and producing "Device unavailable" on first reconnect attempt.
- Added the `Close()` call in both sites that release the stream: `Connect()` (lines 25–26, releasing the prior stream before opening the new device) and `Dispose()` (lines 700–702). The `?.` chain handles the nullable-field case identically to before.
- Added `private bool _disposed` field, mirroring entries 340 (MatrixPollingService, LedPollingService). Set `true` at the *start* of `Dispose()` so a stale call from a poller racing teardown sees the flag before the dispose body completes. Guard added to `SendCommand`: throws `ObjectDisposedException(nameof(VialProtocolService))` instead of NRE-ing on `_stream`. `SendCommand` is the gateway for every read/write — any caller that survives the Dispose race goes through it, so one guard is enough.
- One-shot lifecycle: `Connect()` does *not* reset `_disposed`. The service is constructed once per process, and the existing usage in `MainWindowViewModel` (single field, never re-instantiated) matches that contract. If reconnection-after-dispose is ever needed, that's a separate refactor; the explicit `ObjectDisposedException` makes the misuse loud.
- No new unit test. `HidStream` isn't mockable without wrapping it (out of scope for this fix), and the `_disposed` guard would only trip in a real teardown race that the existing test infra can't synthesise. Plan-noted manual verification: yank cable mid-poll, confirm reconnect succeeds on first re-enumeration.
