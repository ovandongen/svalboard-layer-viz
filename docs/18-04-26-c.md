### 348. `MacroCodec` empty-delay rejection

**Modified:** `src/SvalboardLayerViz.Core/Macros/MacroCodec.cs`, `src/SvalboardLayerViz.Tests/Macros/MacroCodecTests.cs`

- Decoder saw `\x01\x04|` (SS_DELAY_CODE immediately followed by the pipe terminator, no digits between) and coerced to `MacroDelayAction(0)`. Re-encode produces `\x01\x040|` — semantically the same delay value but four bytes instead of three, so the round-trip is not byte-identical. Matches the "refuse to represent what we can't round-trip" stance already applied in entries for 2.2 and 2.3.
- Replaced the `digits.Count > 0 ? int.Parse(...) : 0` ternary with an explicit `if (digits.Count == 0) throw new InvalidDataException(...)`. Error message names the macro index and the SS_DELAY_CODE specifically so a corrupt firmware buffer surfaces with the exact offending position rather than "decode failed somewhere."
- Existing `Decode_DelayNoDigits` test asserted `DelayMs == 0`; replaced with `Decode_DelayNoDigitsThrows` that calls `Assert.Throws<InvalidDataException>`. Test comment explains why silent-to-zero is wrong even though `0` looks like a sensible default — the re-encode divergence is the real failure mode, not the value itself.

### 349. `KeymapEditSession` combo/tap-dance index bounds check

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeymapEditSession.cs`, `src/SvalboardLayerViz.Tests/Keymap/EditSessionDynamicEntryTests.cs`

- `ExecuteForward` / `ExecuteReverse` cases for `SetComboOp` and `SetTapDanceOp` wrote `_currentCombos[co.Index] = ...` with no bounds check. `List<T>`'s indexer does throw on out-of-range, but the `ArgumentOutOfRangeException` message is opaque (just "Index was out of range") and mentions neither the op type nor the list size. Diagnosing an undo-stack divergence from a stack trace would have required reading the calling code to figure out which list was involved.
- Added `private static void ValidateIndex(int index, int count, string opName)` at the bottom of the class. Throws `InvalidOperationException` with `$"{opName} index {index} out of range [0, {count})."` — same exception type and phrasing as the Tier 1.3 default-case throws, so the error surface for "bad op" is uniform.
- `nameof(SetComboOp)` / `nameof(SetTapDanceOp)` for the `opName` parameter; survives rename refactors without silent drift.
- Two new tests: `ApplySetComboOp_OutOfRangeIndex_Throws` uses index 999 against a 2-combo session and asserts the message contains "999" and "SetComboOp"; the tap-dance mirror uses `-1` to cover the negative-index branch as well. Keeps the test count at two (rather than one per bound per type) — the helper is trivial enough that exhaustive boundary coverage is overkill.
- No change to `BuildDeviceWrites` or the `ComboEntryWrite` / `TapDanceEntryWrite` paths — they iterate `PendingComboIndices()`, which is bounded by `_currentCombos.Count` construction-time. The guard only matters for op-application, which is the only surface that takes an externally-supplied index.

### 350. `GetDefinition` sanity-cap + empty-chunk guard

**Modified:** `src/SvalboardLayerViz.Core/Protocol/VialProtocolService.cs`, `src/SvalboardLayerViz.Tests/Protocol/VialProtocolServiceParserTests.cs`

- Two hangs in `GetDefinition`'s paging loop: (a) `GetDefinitionSize()` returns `BitConverter.ToInt32(response, 0)` with no sanity check, so `int.MinValue` or a multi-gigabyte value propagates straight into `new byte[totalSize]` and either OOMs or (for negative) throws `OverflowException` at allocation time; (b) `bytesToCopy = Math.Min(ReportSize - dataOffset, totalSize - offset)` can be ≤ 0 if `dataOffset >= ReportSize` (not reachable via the current `FindXzMagicOffset` since that caps at `ReportSize - XzMagicBytes.Length`, but a future change to the offset logic could regress — defence-in-depth). Loop never advances `offset`, spins forever.
- Added `private const int MaxDefinitionSize = 64 * 1024`. Vial definitions are XZ-compressed JSON; real firmware emits a few KB at most. 64 KB is a generous ceiling that still fails loud on garbage. Reject `totalSize <= 0` and `totalSize > MaxDefinitionSize` with `InvalidDataException` before the allocation. Error message names the reported size and the cap so the diagnosis fits in one log line.
- Added `if (bytesToCopy <= 0) throw` immediately after the `Math.Min`. Message names the block index and the computed `dataOffset` — the two variables needed to reason about which response frame went wrong.
- Three new tests in `VialProtocolServiceParserTests` using the existing `TestableProtocol` harness: negative (`int.MinValue` via `resp[3] = 0x80`), zero (all-zero response), and oversized (100 000 bytes, LE-encoded). All three assert `InvalidDataException` without needing chunk responses queued — the guard fires before any `VialGetDefinition` command is sent.
- Considered but rejected: a fourth test for the `bytesToCopy <= 0` branch. Would require either a test-only hook to force `dataOffset = ReportSize` or a fake `FindXzMagicOffset`. Not worth the harness surface for a branch that can't be reached through the current code path — the guard is tested by reading it exists, the logic is trivially correct.

### 351. Editor-dialog re-entry guards — task-state gates

**Modified:** `src/SvalboardLayerViz.App/App.axaml.cs`

- `OpenMacrosRequested`, `OpenCombosRequested`, `OpenTapDanceRequested` callbacks all read `_ = EditorDialogFactory.ShowXxxEditorAsync(viewModel, mainWindow)`. Discarding the `Task` meant that if the callback fired twice before `ShowDialog` took the modal lock — rapid toolbar double-click, key-binding repeat, or any non-modal command source — two dialogs could stack. The Avalonia modal lock blocks input to the owner once the dialog appears, but the race between fire and show is still open.
- Applied the captured-field pattern from the existing `DiagnosticsWindow` handler immediately below (App.axaml.cs:488-498), adapted: `DiagnosticsWindow` uses `IsVisible` because the factory returns a `Window`; the editors return `Task`, so use `IsCompleted` instead. Three new `Task?` locals (`macroEditorTask`, `comboEditorTask`, `tapDanceEditorTask`) captured in the delegate closure. Callback body: `if (task is { IsCompleted: false }) return; task = EditorDialogFactory.ShowXxxAsync(...)`.
- No signature changes to `EditorDialogFactory` — keeps the fix minimal and leaves dialog-construction plumbing in one place. The factory methods already return `Task`; the gate consumes that contract rather than the factory having to expose a new "is-open" state.
- Skipped `SetKeyLabelRequested` at App.axaml.cs:486. `PromptKeyLabelAsync` is `ShowDialog`-on-mainWindow and the invoker is a UI gesture on an already-modally-blocked owner; no observed dupe and guarding it would add surface without paying for itself. Noted as out-of-scope in the plan for the same reason.
- No new unit test. The behaviour is a pure harness-level discard→gate change; the earliest place to exercise it is in an Avalonia UI test harness, which the project doesn't have set up. Manual check (recorded here for the dev-log audit trail): open Macros editor, click the Macros toolbar button again while it's visible — second click no-ops. Close, click again — opens normally. Repeat for Combos and Tap Dance.
