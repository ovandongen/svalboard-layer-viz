### 352. `AtomicFile` flush-to-disk before rename — entry 343's crash-safety was incomplete

**Modified:** `src/SvalboardLayerViz.Core/Persistence/AtomicFile.cs`

- `AtomicFile.WriteAllText[Async]` from entry 343 wrote to `{path}.tmp` via `File.WriteAllText[Async]`, then `File.Move(tmp, path, overwrite: true)`. The move is atomic at the metadata level, but neither call flushed the bytes to disk first. On NTFS without `MOVEFILE_WRITE_THROUGH`, and on POSIX without `fsync`, buffered bytes sit in the OS page cache while the rename commits to the journal. Power loss between metadata commit and data flush → destination file exists at the new inode but contains zero bytes. Exactly the failure mode entry 343 was supposed to prevent — the helper's docstring claimed "crash mid-write leaves the original file intact" but the crash window actually spans *past* the rename.
- Switched both overloads to explicit `FileStream(tmp, FileMode.Create, FileAccess.Write, FileShare.None)`. Write content, call `fs.Flush(flushToDisk: true)` to force the OS to issue an `fsync` equivalent, dispose (which also closes the handle), *then* `File.Move`. Now a crash before `Flush(true)` returns leaves the tmp potentially empty (recoverable — cleaned up on next `TryDelete`); a crash after `Flush(true)` but before `Move` leaves a complete tmp next to the original (also harmless); a crash after `Move` leaves the new file on disk with all bytes flushed. No window in which the destination exists but is truncated.
- Explicit `FileShare.None` so no other process can read a partially-written tmp. Matches the "atomic or nothing" contract.
- Skipped the POSIX directory `fsync` — no portable BCL call, and the residual window (directory entry not yet fsynced) is orders of magnitude smaller than the page-cache window this fix closes. If it becomes load-bearing, address via a P/Invoke-guarded branch; don't pay the complexity cost yet.
- Content encoding is explicit `Encoding.UTF8.GetBytes(content)` rather than `StreamWriter`, matching the previous `File.WriteAllText` default (UTF-8 without BOM). Avoids a silent BOM introduction that would break the existing JSON readers.
- Docstring updated to describe the real invariant — "flushed to disk (not just the OS page cache)" — so the next reader doesn't have to re-derive why the helper is spelled this way.

No new test. Added plan-explicit: the only *meaningful* test would be a crash simulation that can't be done in xUnit without OS hooks. Adding a test that asserts `Flush(true)` was called via `FileStream` reflection creates a false-positive ("the method is called") without proving the OS-level contract. The existing round-trip tests (entry 343) continue to pass and document that the normal happy path isn't regressed. The correctness claim is by code inspection, noted here for the audit trail.

### 353. Editor-dialog exception observation — `ObserveFaults` helper + fourth site covered

**Modified:** `src/SvalboardLayerViz.App/App.axaml.cs`

- Entry 351's three task-state gates for `OpenMacrosRequested` / `OpenCombosRequested` / `OpenTapDanceRequested` gated re-entry correctly but left exception handling broken: the assigned `Task?` was never awaited. A thrown exception inside `ShowMacroEditorAsync` (e.g. data-binding error, keymap parse) faulted the task; the fault propagated only via `TaskScheduler.UnobservedTaskException` on GC, which in .NET 10 is reliable-eventually but silent-right-now. User sees a dialog that briefly flashes and closes with no error message; log is empty until GC runs. Entry 351 also explicitly deferred `SetKeyLabelRequested` (line 500-501) on the basis that the owner is modally blocked — true for re-entry, wrong for exception visibility.
- Added `private static void ObserveFaults(Task task, string dialogName)`: a `ContinueWith` with `TaskContinuationOptions.OnlyOnFaulted | ExecuteSynchronously` that unwraps via `GetBaseException()` and logs to `DiagnosticLog.Error` under the "EditorDialog" subsystem. `ExecuteSynchronously` keeps the continuation on the UI thread's completion context — no thread-marshal needed since `DiagnosticLog` is thread-safe.
- Wired into all four sites: macro/combo/tap-dance editor opens, plus `SetKeyLabelRequested`. The `SetKeyLabelRequested` case becomes a single-line call (`keyVm => ObserveFaults(factory.Prompt(...), "...")`) — still no re-entry gate there, matching entry 351's original (correct) reasoning that the owner's modal-lock handles that concern.
- Re-entry gate semantics unchanged: `if (task is { IsCompleted: false }) return;` — intentionally treats successful, faulted, and canceled tasks all as "done, a new click may open a fresh dialog". That's the right UX: after a fault the user should be able to retry without restarting the app. The fault that caused the first attempt is now logged, so support can see *why* it failed.
- Comment at the block-start rewrite: entry 351's comment emphasised the modal-lock race; the new comment also names the fault-observation concern so the next reader doesn't have to re-derive why the continuation is there.

### 354. OOM caps for `GetKeymapBuffer` and `GetMacroBuffer` — completing entry 350's pattern

**Modified:** `src/SvalboardLayerViz.Core/Protocol/VialProtocolService.cs`, `src/SvalboardLayerViz.Tests/Protocol/VialProtocolServiceParserTests.cs`

- Entry 350's `MaxDefinitionSize = 64*1024` sanity-cap only guarded `GetDefinition`. Two sibling allocators take network-derived sizes with no equivalent cap: `GetKeymapBuffer(int layers, int rows, int cols)` computes `totalBytes = layers * rows * cols * 2` with args sourced from `GetLayerCount()` (network) and the layout JSON, and `GetMacroBuffer(int bufferSize)` where `bufferSize` comes from `GetMacroBufferSize()` reading BE16 from the wire. A malfunctioning or malicious firmware reporting `layers = 100000` at the Vial layer-count command allocates 12 GB; a macro-size response of 65535 allocates 64 KB for what's normally a few hundred bytes.
- Promoted the single `MaxDefinitionSize` constant into three siblings (`MaxDefinitionSize`, `MaxKeymapSize`, `MaxMacroSize`), all at 64 KB. The old constant stays at its original name so entry 350's reference remains correct; the new ones sit next to it with a comment block explaining the shared rationale. All three are generous ceilings — real firmware values are a few KB, a few hundred bytes, and a few hundred bytes respectively.
- `GetKeymapBuffer`: added `if (layers <= 0 || rows <= 0 || cols <= 0)` early-reject with a message naming all three values, then switched `totalBytes` to `long` computation to survive `int * int * int * 2` overflow (happens at ~32K layers — possible with a garbage `GetLayerCount()` response, not theoretical). After the `> MaxKeymapSize` check passes, cast back to `int` for the allocator. The downstream chunked-read loop is unchanged — it's bounded by `totalBytes` either way.
- `GetMacroBuffer`: added `if (bufferSize <= 0 || bufferSize > MaxMacroSize)` at function entry. Simpler than the keymap case because there's only one size value and `BitConverter.ToUInt16` can't produce a negative (but the check costs nothing and catches a future refactor that might switch to signed 32-bit). Error message names the reported size and the cap — one-line diagnosis.
- Error type is `InvalidDataException`, matching entry 350's idiom for "firmware gave us nonsense". Callers already treat `GetDefinition` OOM as a connection-abort signal; same behaviour for the siblings now.
- Six new tests in `VialProtocolServiceParserTests` mirroring entry 350's three-per-cap pattern: `GetKeymapBuffer_{NegativeDimension,ZeroLayers,OversizedDimensions}_Throws` and `GetMacroBuffer_{NegativeSize,ZeroSize,OversizedSize}_Throws`. The `OversizedDimensions` case uses `layers=100_000` to exercise the long-math overflow branch specifically — if the cast-back-to-int was done before the cap check, this test would silently pass via int overflow producing a small value. Documented in the test comment for future maintainers.
- Considered: fourth test per buffer for the off-by-one upper bound (`= MaxSize` should pass, `= MaxSize + 1` should throw). Rejected — the cap is defence-in-depth with a 64 KB value that's already ~500× typical firmware, so pinning the exact boundary adds test churn without catching real bugs. The existing tests cover the "clearly garbage" region; that's what the cap is for.

## False-alarms logged

Three of the five hostile-review agents surfaced a CRITICAL/HIGH finding that verification disproved. Keeping the list here because the audit trail should show verification, not blind acceptance of agent output:

1. **Protocol agent** — claimed the polling services' `Stop()` method has zero `-= handler` calls, concluding entry 340's fix was fake. Wrong: the subscribe/unsubscribe pair lives in the *ViewModel* (`StopMatrixPolling` at `MainWindowViewModel.cs:686-691`, `StopLedPolling` at `:712-717`). The polling service itself doesn't subscribe to anything — it *publishes* events. Agent conflated "service's internal Stop" with "VM's Stop\*Polling gating".
2. **Codec agent** — claimed `MacroCodec` text-byte 0x01 collision is asymmetric: encode rejects, decode silently mangles. Wrong: the decode text-branch only enters when `buffer[pos] != SsQmkPrefix (0x01)`, so a 0x01 in text flows into the action-branch and either parses as a known action (round-trip closed by the known-action set) or throws via entry 342's unknown-action-byte guard at `MacroCodec.cs:117-122`. Round-trip is closed on both sides.
3. **View-layer agent** — claimed a CTS race in `TryConnectAsync`'s finally: Shutdown could dispose `attemptCts` while the in-flight attempt holds a reference, then the finally calls into a disposed CTS. Half-wrong: `_isConnecting` at line 331 early-exits concurrent attempts, so the *documented* race (two concurrent TryConnects) can't happen. The Shutdown-vs-in-flight interleave is real but harmless — Shutdown's `_connectCts = null` flips the `ReferenceEquals` check false, skipping the redundant dispose; the in-flight attempt's `ct` usage is already guarded by the HidSharp layer's own cancellation handling.

Lesson for future hostile-review loops: agents are useful for breadth and for surfacing where to look, but every CRITICAL claim needs first-hand verification before it enters a plan. The plan file's "Corrections to log" section lists this explicitly.
