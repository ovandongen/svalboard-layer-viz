### 355. Polling services — `volatile bool _disposed`

**Modified:** `src/SvalboardLayerViz.Core/Protocol/MatrixPollingService.cs`, `src/SvalboardLayerViz.Core/Protocol/LedPollingService.cs`

- Both poll loops read `_disposed` on a `Task.Run` background thread, and
  `Dispose()` writes it from the UI thread. Plain-`bool` reads have no memory
  barrier — the JIT is allowed to cache the value in a register across the
  `PollError?.Invoke()` call boundary, so a poller that read `_disposed ==
  false` before Dispose set it to true can still proceed to invoke into an
  already-torn-down VM. Spec-wise undefined on all architectures; the fact
  that it's never reproduced on x86/ARM is a compiler-vendor accident, not
  a guarantee.
- `private bool _disposed;` → `private volatile bool _disposed;` in both
  services. Keyword-only fix; no other code change needed. Reads now have
  acquire semantics, writes have release semantics — the poll loop observes
  the Dispose write on its next iteration.
- No test. Deterministic race-triggering isn't feasible in xUnit (the JIT's
  register-caching is implementation-defined and doesn't surface under
  instrumentation). Correctness by code inspection + ECMA-335 guarantee.

### 356. `MainWindowViewModel.Shutdown` — `Interlocked` gate replaces plain-bool check

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Previous form: `private bool _isShutdown; ... if (_isShutdown) return; _isShutdown = true;`.
  In the common case `Closing` and `Quit` both run on the UI thread and the
  dispatcher serialises them — fine. The race window is `Quit`: any future
  async step that yields puts the UI thread back in the dispatcher queue,
  where a pending `Closing` event can fire. Both paths then pass the
  `if (_isShutdown)` gate (still `false`), run the body, and double-dispose
  `_connectCts` and `_protocolService`. `Cancel()` on a disposed CTS throws
  `ObjectDisposedException` in the dispatcher loop; `Dispose()` on an
  already-disposed protocol service is a no-op but masks the real bug in
  diagnostics.
- Field switched to `private int _isShutdown;` (Interlocked has no bool
  overload — int is the conventional substitute). Guard body is now
  `if (Interlocked.CompareExchange(ref _isShutdown, 1, 0) != 0) return;` —
  atomic test-and-set, one of the two racing callers observes 0→1 and runs
  the body, the other observes 1 and bails.
- Comment block at the field explains *why* an int, not "convert to int
  because type-system": future reader sees the Interlocked-has-no-bool
  constraint and the Closing-during-Quit interleave that forced atomicity,
  doesn't have to re-derive it.
- No test. Same deterministic-timing skip as B.1.

### 357. Async Closing handler + `Shutdown → ShutdownAsync` rename

**Modified:** `src/SvalboardLayerViz.App/App.axaml.cs`, `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Today's `Shutdown()` body is sync-blocking (StopMatrixPolling +
  `_pollTask?.Wait(500)` inside, then sync Disposes). The Closing handler
  was `mainWindow.Closing += (_, _) => { SaveWindowState(); viewModel.Shutdown(); };`
  — sync to match. Forward-looking concern: the moment any new cleanup in
  Shutdown adds an `await`, it becomes fire-and-forget at process exit
  because the handler has no await to propagate. Avalonia closes the window
  and ends the message loop before the continuation runs. Any unsaved state
  or not-yet-released handle leaks.
- `Shutdown()` → `ShutdownAsync() : Task`. Body stays sync-complete for now;
  ends with `return Task.CompletedTask;` rather than `async` marking to
  avoid the CS1998 async-without-await warning. The single internal caller
  (`Quit` relay command) becomes `async Task Quit` and `await ShutdownAsync()`.
  Docstring updated to name the "so any future async cleanup is actually
  awaited" motivation — same anti-rot pattern as B.1's comment block.
- Closing handler rewritten to the canonical cancel-then-async-then-close
  pattern:
  ```csharp
  var closingHandled = false;
  mainWindow.Closing += async (sender, e) =>
  {
      if (closingHandled) return;
      closingHandled = true;
      e.Cancel = true;
      SaveWindowState();
      await viewModel.ShutdownAsync();
      ((Window)sender!).Close();
  };
  ```
  `closingHandled` is a closure-local (not a field) — re-entry is only
  possible within this window instance's lifetime, and the closure captures
  it uniquely per wiring. `e.Cancel = true` prevents Avalonia from tearing
  down the window before ShutdownAsync completes; the final `.Close()`
  re-enters the handler, which early-returns on the flag and lets Avalonia
  dispose the window normally.
- No test — Avalonia UI harness still absent (same skip noted across
  sessions). Manual smoke on `dotnet run`: close via title-bar X, close via
  Quit command — both still exit cleanly.
- Build clean; no new warnings.

### 358. `SetQmkSettingOp` — `ValidateSettingId` guards against dictionary-append

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeymapEditSession.cs`, `src/SvalboardLayerViz.Tests/Keymap/KeymapEditSession_QmkSettings_Tests.cs`

- Entry 349 added `ValidateIndex` to `SetComboOp`/`SetTapDanceOp` because the
  `List<T>` indexer throws an opaque `ArgumentOutOfRangeException`.
  `SetQmkSettingOp` writes into `_currentSettings[so.SettingId] = so.NewValue`
  where `_currentSettings` is a `Dictionary<ushort, ushort>`. Dictionary's
  indexer-assignment *creates* a new entry for an unknown key — no throw, no
  diagnostic. A typo'd `SettingId` silently appends a phantom setting to the
  edit session's pending state; that phantom then gets included in
  `BuildDeviceWrites` and pushed to the firmware on save. Worse, the
  identical silent-append happens in `ExecuteReverse` on Undo.
- New `private void ValidateSettingId(ushort id)` helper mirroring
  `ValidateIndex`: checks `_currentSettings.ContainsKey(id)`, throws
  `InvalidOperationException` with `0x{id:X4}` and the op name. Called at
  the top of both `SetQmkSettingOp` branches (Forward + Reverse). Settings
  are device-loaded at session construction so any ID not-already-present
  is by definition wrong — no edge case where we'd want to allow it.
- Comment above the helper names the dictionary-append semantics so the
  next reader doesn't have to chase why the check exists.
- One new test in `KeymapEditSession_QmkSettings_Tests`:
  `Apply_SetQmkSettingOp_UnknownSettingId_Throws`. Mirrors the
  combo/tap-dance bounds-test pattern — construct a session with known
  settings, attempt a `SetQmkSettingOp` with an unknown ID (`0x00FE` chosen
  to be clearly outside the sample set), assert `InvalidOperationException`
  with the bad ID in the message.
- Not extended to `SetKeyOp` — writes into a 3-D `ushort[,,]` array which
  throws `IndexOutOfRangeException` natively. Same vulnerability surface
  with worse error text, but deferred per the master plan's low-priority
  note; adding a bounds guard there without the ExecuteReverse case would
  be asymmetric.

### 359. Test-honesty bundle — four tightening items in one commit

**Modified:** `src/SvalboardLayerViz.Tests/Persistence/AtomicFileTests.cs`, `src/SvalboardLayerViz.Tests/Settings/SettingsServiceTests.cs`, `src/SvalboardLayerViz.Tests/Protocol/PollingServiceSubscriptionTests.cs`, `src/SvalboardLayerViz.Tests/Keymap/EditSessionDynamicEntryTests.cs`

Per the master plan: bundle these as a single housekeeping commit — they
share the "test asserts the wrong thing / too loosely" theme and aren't
independently reviewable.

- **`AtomicFileTests.WriteAllText_WriteFails_OriginalPreserved`** — new test.
  Existing tests only cover the success path (round-trip + cleanup of tmp
  on success). The *crash-safety* claim — original untouched when the write
  fails — was unverified. Can't do true mid-flush crash simulation without
  OS hooks, but we can simulate a write-open failure: pre-create `{path}.tmp`
  as a directory, so the FileStream constructor fails before any bytes are
  written. On POSIX and Windows this throws `UnauthorizedAccessException`
  (not `IOException` as initially written — the test had to widen to
  `Assert.ThrowsAny<Exception>` after the first run failed on macOS;
  documented in a comment since the claim under test is preservation, not
  exception shape). Asserts the original "original" content is unchanged.
- **`SettingsServiceTests.Load_OlderSchemaVersion_MigratesAndPersists`** —
  tightened. Previous form ran `Load()` twice and asserted the second
  returned the migrated schema version. That can pass even if `Save()`
  silently failed and the second `Load()` simply re-ran the migration
  branch in memory. Added an intermediate `File.ReadAllText` + `JsonDocument`
  parse to prove the *on-disk* bytes carry `"SchemaVersion": 1`, pinning the
  persistence claim rather than the in-memory migration. The re-`Load()`
  assertion stays as regression coverage but is no longer load-bearing.
- **`PollingServiceSubscriptionTests` — both `*_Dispose_DoesNotFireErrorAfterDispose`**
  rewrites. Previous form: `Thread.Sleep(150); Assert.Equal(countAtDispose, errorCount);`
  — asserts counter-didn't-advance-within-a-window. CI slowdown or a GC
  pause could keep the poll thread from running again within 150 ms, so
  the test would pass whether or not the subscription leak existed.
  Swapped to `ManualResetEventSlim` set *inside* the PollError handler
  when a `disposed`-flipped volatile flag says we're post-Dispose. If a
  handler fires after Dispose, the event sets and `Wait(150)` returns
  true, failing the test. `Volatile.Read/Write` on the int flag ensures
  the flip isn't reordered past `sut.Dispose()`.
- **`EditSessionDynamicEntryTests` — four new boundary cases**:
  `ApplySetComboOp_IndexEqualCount_Throws`,
  `ApplySetComboOp_IndexCountMinusOne_Succeeds`,
  `ApplySetTapDanceOp_IndexEqualCount_Throws`,
  `ApplySetTapDanceOp_IndexCountMinusOne_Succeeds`. Existing tests used `999`
  and `-1`, which catch the clearly-out-of-range case but not the canonical
  off-by-one — a `>= count` → `> count` regression in `ValidateIndex` would
  slip past. `index = count` is the inclusive boundary (must throw);
  `index = count - 1` is the positive control (must NOT throw). Four tests
  because the failure shape differs between Combo and TapDance ops.
