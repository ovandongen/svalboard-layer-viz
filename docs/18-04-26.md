### 340. PollError handler leak — named handlers + post-Dispose guard

**Modified:** `src/SvalboardLayerViz.Core/Protocol/MatrixPollingService.cs`, `LedPollingService.cs`, `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`
**Added:** `src/SvalboardLayerViz.Tests/Protocol/PollingServiceSubscriptionTests.cs`

- `StartMatrixPolling` / `StartLedPolling` subscribed inline lambdas to `PollError` capturing `StatusMessage`. The `Stop*Polling` siblings only unsubscribed `MatrixStateChanged` / `LedColorChanged`. Every toggle of Live Highlighting or LED polling — and every disconnect/reconnect cycle — leaked a closure rooted to the VM.
- Replaced the lambdas with named instance methods `OnMatrixPollError(string)` / `OnLedPollError(string)` and added the symmetric `-=` in the corresponding `Stop*Polling`. Now subscribe/unsubscribe paths are visibly mirror-image.
- Added `_disposed` flag in both polling services, set true at the *start* of `Dispose()`. `PollLoop`'s catch arm now guards `if (!_disposed) PollError?.Invoke(ex.Message)`, so an in-flight poll that throws after `Stop()` has been called doesn't call back into a torn-down VM. `Dispose()` also nulls the event delegates after `Stop()` so any residual subscribers from external code don't keep references alive.
- Test file uses a `ThrowingProtocolService` (every read throws) to drive the catch path, then asserts `errorCount` doesn't change between the `Dispose()` snapshot and a 150 ms quiet period. A second test exercises 5× start/stop cycles with a normal fake to confirm no stuck threads or thrown exceptions on rapid subscription churn.

### 341. Window-X close path bypassed cleanup — `Shutdown()` extracted

**Modified:** `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`, `src/SvalboardLayerViz.App/App.axaml.cs`

- `_deviceSubscription.Dispose()` and `_protocolService.Dispose()` lived only inside the `Quit` command. Closing via the title-bar X fired Avalonia's `Closing` event (which only ran `SaveWindowState`) and skipped the rest. `OnDeviceListChanged` kept calling back into a disposed VM and the HID stream lingered until process exit, sometimes blocking re-enumeration on the next launch.
- Extracted `Shutdown()` on `MainWindowViewModel`: stops both polling services, disposes the device subscription, cancels and disposes `_connectCts`, disposes the protocol service. Idempotent via `_isShutdown` guard so it's safe to call from both close paths.
- `Quit` is now `Shutdown(); QuitRequested?.Invoke();` — dropped the `Environment.Exit(0)` fallback that hid the case where `QuitRequested` was unwired.
- `App.axaml.cs` `mainWindow.Closing` handler now calls `SaveWindowState()` then `viewModel.Shutdown()`. The existing `QuitRequested` callback is unchanged; `Closing` fires before `Environment.Exit` so both routes converge through the same teardown.
- Note: this also closes `_connectCts` in the close path, which overlaps with Tier 2.6's "dispose-and-replace per-attempt" fix. Left the per-attempt pattern alone — that's a different concern (concurrent connect attempts during normal operation, not shutdown).

### 342. `KeymapEditSession` switch statements — default arm enforces exhaustiveness

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeymapEditSession.cs`, `src/SvalboardLayerViz.Tests/Keymap/KeymapEditSessionTests.cs`

- `ExecuteForward` and `ExecuteReverse` switched on `EditOp` subtypes with no default. Adding a sixth `EditOp` (e.g. `SetTapDanceOp` was added in entry 309) but only wiring it through one of the two methods would silently diverge the undo stack from `_current` state. `BuildDeviceWrites()` would then synthesise wrong writes from the diverged `_current`, corrupting device state on the next save with no exception, no log entry, no test failure.
- Added `default: throw new InvalidOperationException("Unhandled EditOp subtype: {name}")` to both methods. Cheap to write, cheap to maintain, loud when violated.
- Test defines a sealed `UnknownOp() : EditOp` record local to the test class and asserts `Apply()` throws with the type name in the message. One test is enough — `Apply` flows through `ExecuteForward`, and `Undo` would flow through `ExecuteReverse` only if a malformed op had already been pushed; the same default-arm pattern in both methods is the proof.
- Original plan's "Mirror in `Apply()`" note was imprecise: `Apply` itself has no switch, it just delegates. The fix is in the two execute methods only.

### 343. Atomic JSON writes — `AtomicFile` helper, applied to snapshots and settings

**Added:** `src/SvalboardLayerViz.Core/Persistence/AtomicFile.cs`, `src/SvalboardLayerViz.Tests/Persistence/AtomicFileTests.cs`
**Modified:** `src/SvalboardLayerViz.Core/History/SnapshotService.cs`, `src/SvalboardLayerViz.Core/Settings/SettingsService.cs`, `src/SvalboardLayerViz.Tests/Settings/SettingsServiceTests.cs`

- `SnapshotService.CaptureAsync` / `ExportAsync` / `ImportAsync` and `SettingsService.Save` all called `File.WriteAllText[Async]` directly. A crash mid-write left a truncated file. Next `SettingsService.Load()` swallowed the parse error in a blanket `catch { return new UserSettings(); }` — the user lost every setting on the first interruption with no signal.
- `AtomicFile.WriteAllText` / `WriteAllTextAsync` writes to `{path}.tmp` first, then `File.Move(tmp, path, overwrite: true)`. The Move on POSIX is atomic via `rename(2)`; on NTFS, `File.Move` with `overwrite: true` falls back to `MoveFileTransacted`-equivalent semantics. Either way: a crash before the Move leaves the original intact and a stale `.tmp` alongside (no harm — next successful write overwrites it). Cleanup on failure deletes the orphan tmp; the cleanup itself is best-effort and never re-throws.
- `SettingsService.Load` now distinguishes the failure modes that previously hid behind the catch-all: `JsonException` → `DiagnosticLog.Error` "Parse failed at {path}: {msg}; using defaults"; `IOException` / `UnauthorizedAccessException` → `DiagnosticLog.Warn` with the underlying message. Other exception types propagate (they indicate bugs, not file corruption — the old code swallowed `NullReferenceException` etc., which is exactly the failure mode that hides logic errors during refactors).
- Tests cover: new file via atomic move, replacement via atomic move, no orphan `.tmp`, async overload, and (on missing parent dir) the cleanup branch fires and leaves no residue. `SettingsServiceTests` gets `Load_TruncatedJson_ReturnsDefaults` (asserts behavior identical to old catch-all from caller's perspective) and `Save_OverwritesViaAtomicMove_NoOrphanTmp`.

### 344. `UserSettings.SchemaVersion` — versioning + migration scaffolding

**Modified:** `src/SvalboardLayerViz.Core/Settings/UserSettings.cs`, `src/SvalboardLayerViz.Core/Settings/SettingsService.cs`, `src/SvalboardLayerViz.Tests/Settings/SettingsServiceTests.cs`

- `KeymapSnapshot` carried a `CurrentSchemaVersion = 4` and an explicit version field; `UserSettings` carried nothing. The first breaking change to `UserSettings` (rename, type change, new required field) would have nuked every existing user's settings via the catch-all in `Load` — and now, post-entry-343, would have logged a `JsonException` first, but still nuked them.
- Added `public const int CurrentSchemaVersion = 1;` and `public int SchemaVersion { get; init; } = CurrentSchemaVersion;` on `UserSettings`. New files are stamped with the current version on first `Save`.
- `SettingsService.Load` after successful deserialize:
  - **Future-version file** (`parsed.SchemaVersion > CurrentSchemaVersion`): copy to `{path}.v{N}.bak`, log warn, return defaults. Backing up rather than overwriting protects users who downgrade, and protects fields the older code doesn't know about from being silently dropped on the next Save.
  - **Older-version file** (`parsed.SchemaVersion < CurrentSchemaVersion`): call `MigrateSettings(parsed)` and immediately `Save(migrated)` so the file gets the current version stamp. Today this is a no-op (we are at v1) — `MigrateSettings` just stamps `CurrentSchemaVersion` and returns. Future schema bumps add a switch on the old version with one arm per migration. The placeholder exists so the first real schema change has a defined landing spot rather than bolting migration logic into `Load` under deadline.
  - **Equal**: return as-is.
- Tests cover the three branches: future-version backs up + returns defaults (asserts `.v999.bak` exists), current-version round-trips fields intact, older-version (forced via explicit `"SchemaVersion": 0` payload — the field's default would otherwise mask the branch) migrates and persists, with the persistence verified by a re-Load returning the bumped stamp.
