# Changes — 19-04-26-b

## Layer-aware TRNS resolution (QMK runtime semantics)

Followed the earlier review/cleanup day (see `19-04-26.md`) with a
behaviour fix the user reported on-device: the mouse layer (L15) showed
TRNS keycodes pulled from intermediate layers that the firmware never
actually emitted. Viz lied. 1205 tests passing (+14 vs `19-04-26.md`'s
1191); branch `develop`, working tree dirty for review.

Root cause: `TransparentKeyResolver` walked **every** lower layer
top-down. QMK at runtime only consults layers that are **active** when
the key is pressed. For an orphan layer (reached via firmware-side logic
not visible in the keymap, e.g. the mouse layer), the only active layers
are L0 and the orphan itself — any intermediate layer's non-TRNS key is
irrelevant to what the keyboard actually sends.

Fix: build a per-layer activation graph from the keymap's layer-switch
keys, compute the active stack for each layer, walk TRNS fallthrough
against that stack only.

**Svalboard wrinkle.** Thumb cluster cols 2 and 5 are physically coupled
on the hardware: a soft press engages col 2, a harder press
additionally engages col 5. So if (row, 2) and (row, 5) on the same
source layer both activate layers, both targets are simultaneously
active during the hard press. Baked into the graph.

### 365. `ActivationHop` + `LayerActivationGraph` — new graph builder

**Added:** `src/SvalboardLayerViz.Core/Keymap/ActivationHop.cs`,
`src/SvalboardLayerViz.Core/Keymap/LayerActivationGraph.cs`

- `ActivationHop` is a 5-field readonly record struct:
  `(SourceLayer, Row, Col, TargetLayer, SwitchType)`. One hop per
  activator key (MO/LT/TG/TO/OSL/LM/DF). Record struct, not class —
  hops live in per-layer path lists that never mutate and the
  equality + hashing the struct gives for free simplified the BFS
  visited-set bookkeeping.
- `LayerActivationGraph.Build(layers)` returns
  `IReadOnlyDictionary<int, IReadOnlyList<ActivationHop>>`, one ordered
  path per layer from L0 upward. Implementation:
  1. Single pass over all layers' keys builds
     `incoming[targetLayer] = List<ActivationHop>`. Self-loops
     (`MO(N)` on L N — the canonical "hold-to-stay" pattern) are
     excluded: they don't *advance* the stack, they only let you
     continue holding.
  2. Each incoming list is sorted `(SourceLayer, Row, Col)` for
     deterministic tie-break — two paths to the same layer pick the
     lowest source first. The sort makes the BFS output stable across
     runs even when the firmware reports keys in nondeterministic order.
  3. Per target layer, BFS backwards from target through reverse edges
     until we reach L0. Standard `parent[sourceLayer] = hop` bookkeeping,
     then forward reconstruction by following `parent[0]` → `parent[next]`
     → … until we hit the target. The safety counter in the reconstruction
     loop is defensive, not load-bearing — BFS dedup via `visited` HashSet
     already prevents cycles, but the counter converts a would-be infinite
     loop into `Array.Empty<>()` if the invariant ever breaks.
  4. **Press-through coupling** in `FindCoHop`: when expanding a hop,
     check if its `(row, col)` has a Svalboard coactivated position
     (see 367 below). If so, search other `incoming` lists for an
     activator at `(hop.SourceLayer, coRow, coCol)` — same source
     layer, thumb col 2 vs col 5. If found, attach as `parentCoHop[x]`
     and the reconstruction inserts the co-hop *before* the primary
     hop in forward order. "Before" matches the physical press sequence
     (col 2 engages first, col 5 adds on hard press).
  5. Cycles and orphans both fall through to `Array.Empty<>()` →
     caller treats as "fallback stack [0, L]".
- `GetActiveStack(layerIndex, path)` helper builds
  `[0, hop1.Target, hop2.Target, …, last.Target]` where last.Target
  *must* equal layerIndex by construction. Empty path →
  `[0, layerIndex]` fallback.
- Not an interface / DI: pure computation, no I/O, called once per
  load / post-save. Static matches `TransparentKeyResolver`'s pattern
  directly below it in the folder.

### 366. `TransparentKeyResolver` — walks active stack, records source

**Modified:** `src/SvalboardLayerViz.Core/Keymap/TransparentKeyResolver.cs`

- Signature widened:
  ```csharp
  public static void Resolve(
      List<Layer> layers,
      IReadOnlyDictionary<int, IReadOnlyList<ActivationHop>>? activationPaths = null)
  ```
  `activationPaths` optional with `null` sentinel = "treat every layer
  as orphan" (preserves behaviour for callers that haven't wired the
  graph yet, like the existing `TransparentKeyResolverTests` which
  construct tiny 1-2-layer setups with no MO keys at all).
- Walk order: previously `for (below = layerIdx - 1; below >= 0; below--)`.
  Now walks the active stack top-down, skipping the current layer
  itself (it's TRNS by construction at this slot). First non-TRNS hit
  wins.
- Two new `Key` fields get set on a resolution hit:
  `ResolvedFromLayer = below` (the layer the effective label came from)
  stored alongside the existing `EffectiveLabel` propagation. Tooltip
  uses this without re-walking.
- `indexByLayer` precomputation pattern kept verbatim from the prior
  implementation — O(keys) per layer, once, before the resolution
  double-loop.

### 367. `SvalboardLayout.GetCoactivatedPositions` — press-through rule

**Modified:** `src/SvalboardLayerViz.Core/Layout/SvalboardLayout.cs`

- One new static:
  ```csharp
  public static IEnumerable<(int Row, int Col)> GetCoactivatedPositions(int row, int col)
  {
      if ((row == 0 || row == 5) && col == 5)
          yield return (row, 2);
  }
  ```
- Deliberately lives in `SvalboardLayout` next to the physical
  position data, not in `LayerActivationGraph`. Reason: the coupling
  is a **hardware** fact about the Svalboard thumb cluster, not a
  graph-traversal concern. If a second board ever gets supported, the
  activation graph stays board-agnostic and the coupling rule moves
  with its layout.
- Rows 0 and 5 are the only rows with a col 5 (verified in the
  `_positions` array: L-Thumb row 0 has 6 keys across cols 0-5, same
  for R-Thumb row 5; finger-cluster rows 1-4 and 6-9 stop at col 4).
  No other board row has a col 5 to even ask about, but the guard is
  cheap and the method is self-documenting.

### 368. `Layer.ActivationPath` + `Key.ResolvedFromLayer` — new record fields

**Modified:** `src/SvalboardLayerViz.Core/Models/Layer.cs`, `src/SvalboardLayerViz.Core/Models/Key.cs`

- `Layer.ActivationPath` (`IReadOnlyList<ActivationHop>`, default `[]`)
  carries the graph's path for each layer into the ViewModel layer so
  the tooltip can display it without the view layer depending on
  `LayerActivationGraph` directly. Empty for L0; empty + orphan for
  layers with no traceable activation.
- `Key.ResolvedFromLayer` (`int?`, default null) on transparent keys
  where `EffectiveLabel` was set — the source layer the label came
  from. Null on L0, null on unresolved TRNS (orphan + lower layers all
  TRNS at that slot), null on non-transparent keys.
- `using SvalboardLayerViz.Core.Keymap;` added to `Layer.cs` — now
  references `ActivationHop`. `Key.cs` didn't need the using; its new
  field is just `int?`.

### 369. Loader + post-save VM — build graph before resolving

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeymapLoader.cs`,
`src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Both callsites of `TransparentKeyResolver.Resolve` got the same
  three-line wrapper before the call:
  ```csharp
  var activationPaths = LayerActivationGraph.Build(layers);
  for (var i = 0; i < layers.Count; i++)
      if (activationPaths.TryGetValue(i, out var path))
          layers[i] = layers[i] with { ActivationPath = path };
  TransparentKeyResolver.Resolve(layers, activationPaths);
  ```
- `KeymapLoader.cs` line 174 (full device load) and
  `MainWindowViewModel.cs` line 1397 (post-save refresh) both apply.
  The post-save path is important: after an edit lands via
  `SaveFlowExecutor`, the keymap is re-read from the device and
  TRNS must re-resolve. If the edit *created* a new activator (say,
  the user assigned MO(5) to a previously plain key), every TRNS on
  L5+ should pick up the new activation path. Without the graph
  rebuild at line 1397, they wouldn't.
- Scope limitation (documented, not fixed): TRNS does **not**
  re-resolve live while the user is in edit mode. Changing
  `MO(2) → MO(4)` on a pending-edit key doesn't rebuild the graph
  until save completes. Matches current behaviour around every other
  TRNS-dependent display state (the whole `TransparentKeyResolver`
  pipeline runs post-save only). Revisit if users report it.
