### 361. `KeycodeService` — constructor accepts the three configuration collections

**Modified:** `src/SvalboardLayerViz.Core/Keymap/KeycodeService.cs`

- Item 2 in the rethink list (rank 1: removes a silent-failure mode).
  `KeycodeService` had a parameterless constructor + three setters
  (`SetCustomKeycodes`, `SetCustomKeyLabels`, `SetMacroPreviews`).
  Resolution order: `Resolve(keycode)` consults the three
  external-configuration collections to translate custom keycodes,
  user-supplied labels, and macro previews. If `Resolve` was ever
  called between construction and the first setter, custom keycodes
  silently fell back to `0xNNNN` hex labels — visible in the UI as
  raw hex with no diagnostic, no error, no warning.
- New constructor:
  ```csharp
  public KeycodeService(
      IReadOnlyList<CustomKeycode>? customKeycodes = null,
      Dictionary<string, string>? customKeyLabels = null,
      IReadOnlyList<string>? macroPreviews = null)
  ```
  All three optional with defaults so the parameterless construction
  pattern still compiles. The setters stay — they're load-bearing for
  *runtime* updates: `SetMacroPreviews` is called after the deferred
  macro load completes (`MainWindowViewModel.UpdateMacroPreviews`),
  `SetCustomKeyLabels` is called from `ApplySettings` when the user
  edits unknown-keycode labels in the settings dialog. Removing the
  setters would require either rebuilding `KeycodeService` on every
  macro load + every settings save (cascades through `WithResolvedLabels`
  callers) or making the service immutable + reactive (much larger
  change). Constructor + setters split is the right contract: ctor for
  startup-known data, setters for live updates.
- Docstring on the constructor names the silent-fallback motivation so
  the next reader sees *why* the optional ctor params exist alongside
  the setters. Same anti-rot pattern the `-e` Interlocked block used.

### 362. `IDeviceConnectionService` extracted; VM accepts both new services as injection points

**Added:** `src/SvalboardLayerViz.Core/Device/IDeviceConnectionService.cs`
**Modified:** `src/SvalboardLayerViz.Core/Device/DeviceConnectionService.cs`, `src/SvalboardLayerViz.Core/Device/DeviceSession.cs`, `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Item 3 in the rethink list (rank 3: cleanup-while-you're-in-the-file).
  Pre-rework, `MainWindowViewModel` injected three services
  (`ISettingsService`, `IVialProtocolService`, `ISnapshotService`) but
  `new()`'d the other two inline (`DeviceConnectionService`,
  `KeycodeService`). Inconsistent — and the inline news made VM
  lifecycle tests untestable without real HID hardware (the whole
  reason 364 below was previously impossible).
- `IDeviceConnectionService` interface extracted with the two-method
  surface (`FindVialDevices()`, `OnDeviceListChanged(Action)`).
  Concrete `DeviceConnectionService` implements it. Class kept; only
  the declaration changed. `LedProbe.cs` in the Debug project uses
  concrete `new DeviceConnectionService()` and still compiles unchanged
  — no breaking change at the production callsite.
- `DeviceSession.Connect`'s first parameter type relaxed from
  `DeviceConnectionService` to `IDeviceConnectionService`. No body
  change — only the static method signature.
- `MainWindowViewModel` constructor expanded:
  ```csharp
  public MainWindowViewModel(
      ISettingsService? settingsService = null,
      IVialProtocolService? protocolService = null,
      ISnapshotService? snapshotService = null,
      IDeviceConnectionService? deviceService = null,
      KeycodeService? keycodeService = null)
  ```
  New parameters appended at the end so existing positional callers
  (`new MainWindowViewModel(_settings, _protocol)` in `EditModeTests`
  etc.) still compile without source change. Defaults match the prior
  inline-`new()` behaviour exactly: `new DeviceConnectionService()` and
  `new KeycodeService()` (parameterless ctor — production wiring sets
  the collections via `KeymapLoader` later, where they're available).
- `KeycodeService` deliberately not made into an interface. App-side it
  stays a concrete dependency. Reason: `KeycodeService` is a
  pure-translator with no I/O — fakes would only exist for testing

  KeycodeServiceTests. Adding an interface for symmetry would be
  rethink-item-3-symmetry-debt of its own kind. Kept concrete; ctor
  injection is enough.

### 363. `App.axaml.cs` — three startup `settingsService.Load()` calls collapse to one

**Modified:** `src/SvalboardLayerViz.App/App.axaml.cs`

- Item 7 in the rethink list (rank 7: trivial cleanup).
  Pre-rework: `OnFrameworkInitializationCompleted` loaded settings
  three times — once for culture init at the top, once for window
  geometry restore, once for hotkey registration, and `MainWindowViewModel`
  loaded a fourth time inside its own constructor. Each reads the same
  JSON file; cost negligible (~1 ms × 4) but the pattern says "I'm not
  sure when settings change" to anyone reading.
- `MainWindowViewModel`'s constructor already loads settings into a
  local `initialSettings` (entry 361's reorganisation made this the
  single read). The App-side `settingsService.Load()` calls at the
  window-geometry block (line 70), the hotkey registration block (line
  731), and the help-on-first-launch block (line 753) all reread the
  same data. Replaced with field-access on the existing `initialSettings`
  variable already in scope at construction, threaded down to the three
  later sites.
- Three Loads intentionally kept:
  1. `SaveWindowState()` — the read-then-write-back pattern needs a
     fresh read to avoid clobbering settings the user changed since
     startup. Documented inline.
  2. The export-flow `settings.Load()` — colors may have been edited via
     the settings dialog mid-session; the export must use current values.
  3. The help-window-close save — read fresh to set `HasSeenHelp` without
     overwriting concurrent settings edits.
- No tests added — change is "n calls collapse to one" with no
  behaviour delta on success path. Verified by spot-check that the
  values pulled from `initialSettings.HotkeyKey` etc. match what
  `settings.Load().HotkeyKey` would have returned at the same moment
  in the startup flow.

### 364. `MainWindowViewModelLifecycleTests` — five lifecycle tests + fake device service

**Added:** `src/SvalboardLayerViz.Tests/Device/FakeDeviceConnectionService.cs`, `src/SvalboardLayerViz.Tests/ViewModels/MainWindowViewModelLifecycleTests.cs`
**Removed:** `src/SvalboardLayerViz.Tests/ViewModels/MainWindowViewModelShowTests.cs`
**Modified:** `src/SvalboardLayerViz.Tests/Protocol/FakeVialProtocolService.cs`, `src/SvalboardLayerViz.App/ViewModels/MainWindowViewModel.cs`

- Item 1 in the rethink list (rank 2: highest-value test debt). Pre-
  rework `MainWindowViewModelShowTests` had two trivial tests covering
  the `ShowWindowRequested` callback pattern — neither actually
  instantiated the VM (the file's own header noted this:
  *"because its constructor requires USB device access"*). Now that
  362 made the device service injectable, that excuse is gone.
- `FakeDeviceConnectionService`: in-memory implementation seeded with a
  `Devices` list (default empty), an optional `EnumerationException`
  the `FindVialDevices` call throws instead of returning, and a captured
  `LastCallback` so tests could fire the device-list-changed event by
  hand. Subscription dispose is counted for symmetry with the device-
  list-changed assertions.
- `FakeVialProtocolService.Dispose()` previously a no-op; now
  increments `DisposeCount`. Needed for the double-shutdown
  assertion. Pure additive — existing tests don't observe it.
- `MainWindowViewModel.TryConnectAsync` access widened from `private`
  to `internal`. The single production caller is
  `InitializeDeviceConnection` which fires it as `_ = TryConnectAsync()`
  (deliberately fire-and-forget so the UI thread doesn't block on HID
  enumeration). Tests need to *await* a connect attempt to assert its
  outcome; `internal` exposes that without changing production
  semantics. `InternalsVisibleTo` was already wired
  (`SvalboardLayerViz.App.csproj:48`), so no project-file change
  needed. Docstring updated to document the test-seam motivation.
- Five tests written:
  1. `Constructor_AppliesPersistedSettings_ToObservableProperties` —
     persists non-default `AlwaysOnTop`, `BackgroundOpacity`,
     `VerticalLayout`, `VerticalLayoutTopHand`, then checks the VM
     constructor reads them. Covers the wiring `initialSettings` →
     `IsAlwaysOnTop` etc. that 363 above consolidated.
  2. `Constructor_CorruptSettingsFile_FallsBackToDefaultsWithoutThrowing`
     — writes `"{ this is not valid json"` to the settings path,
     constructs the VM, asserts no throw + observable-property values
     match `new UserSettings()`. Catches the case where future settings
     work might propagate JSON exceptions out of `Load` instead of
     silently falling back. First write of this assertion failed because
     I'd hardcoded `Assert.False(IsAlwaysOnTop)` without checking that
     `UserSettings.AlwaysOnTop`'s default is `true`. Switched to
     comparing against `new UserSettings()` defaults so the test stays
     correct if defaults change later.
  3. `TryConnectAsync_NoDevicesFound_SetsNoDeviceStatusMessage` — fake
     returns empty list, asserts `IsConnected == false` and the
     status-bar text contains "No Svalboard found". Substring match,
     not full-string compare, so locale-independent.
  4. `TryConnectAsync_HidEnumerationThrows_StatusMessageReflectsFailure`
     — fake throws `InvalidOperationException("boom")`,
     asserts `IsConnected == false`, status contains "Connection error"
     and "boom". Pinned the exception-message-in-status path that the
     `-d` session widened (entry 350-ish — full `ex.Message` instead of
     `ex.GetType().Name` to keep diagnostics actionable).
  5. `ShutdownAsync_CalledTwice_DisposesProtocolOnlyOnce` — the
     load-bearing test for entry 356 (the `-e` Interlocked gate). Calls
     `ShutdownAsync()` twice in a row, asserts `protocol.DisposeCount ==
     1`. Without the gate, this would be 2 — and on the real
     `VialProtocolService` the second `Dispose` would still be a no-op
     but the `_connectCts.Dispose()` second call would throw
     `ObjectDisposedException`, which is precisely the bug the gate
     prevents.
- Old `MainWindowViewModelShowTests.cs` deleted entirely. Its two
  tests asserted the C# `Action?` invocation pattern (`callback?.Invoke()`)
  rather than anything VM-specific — net negative as test coverage,
  noise-positive in the test report.
- Build clean (two pre-existing xUnit1031 warnings on
  `MatrixPollingServiceTests`, unchanged); 1191/1191 tests pass.
